第三篇章 · RAG 与知识库

切片与清洗：喂进 RAG 之前要做什么

你把员工手册 PDF 丢进 RAG，问「年假怎么算」，它答错了。不是模型不行，是那条规则跨了三页，被切成三块，只召回了中间那块。

RAG 的效果，八成取决于切片

大多数人调 RAG 的顺序是：换模型 → 调 Prompt → 加重排序。但真正的瓶颈通常在最前面那一步：文档是怎么被切开的。

检索召回的是「块」。块切错了，后面全错——模型只能看到给它的那一块，看不到被切走的部分， 而且它不知道自己看不到，于是会基于半条规则给你一个完整的答案。

HR 文档的四个特殊性
特点切错了会怎样怎么处理
① 有层级 按字数切会把「第 8 条」拦腰截断 沿结构切：章 → 条 → 款。一条就是一块，宁可块大小不均
② 有交叉引用 「详见第 12 条」被切走后，答案缺一半 切片时把引用目标一起带上，或在元数据里记录引用关系
③ 有版本 它引了 2024 版的旧规则，而且语气一样自信 元数据必带版本与生效日期；旧版要下线，不是留着
④ 有适用范围 「仅适用于正式员工」在标题里，被切掉了 → 它把规则套给了实习生 每块都带上父标题，适用范围写进元数据
第 ④ 条是 HR 文档特有的坑，而且后果最严重。 制度里的适用范围经常写在章节标题或开头一句，正文里不重复。 按字数切片会把它丢掉，于是一条只适用于北京地区正式员工的规则，被讲给了所有人听。
清洗：这三样必须去掉
要去掉的为什么
页眉页脚「第 3 页 共 28 页」「XX公司内部资料」会混进每一块，稀释语义、污染检索
水印文字同上，而且它会被当成正文内容读进去
扫描件的 OCR 噪声OCR 错字在制度文档里是灾难：「不得少于」被识别成「不得多于」意思完全反了。扫描件必须人工抽检

表格要单独处理。把表格拍平成文字会丢掉行列关系——薪酬标准表、假期天数表被拍平之后， 它会把某个职级的数字安到另一个职级头上。表格要么保留结构（转成 Markdown 表格），要么单独存成结构化数据。

验收：看召回的块，不要只看答案
✕ 只看答案对不对 问 20 个问题，答对 18 个，觉得没问题。
→ 但其中可能有几个是模型自己猜对的，检索压根没召回正确的块。 这种「侥幸对」在换个问法、换个模型之后就会变成错。
✓ 看召回 每个问题都检查：召回的前 3 块里，有没有真正包含答案的那一块？
这个指标（召回命中率）才是 RAG 的真实水平。答案正确率会骗你，召回命中率不会。
怎么做

沿结构切、带元数据、验召回不验答案

  1. 沿结构切，不按字数切。制度文档一条就是一块，块大小不均没关系。
  2. 每块带父标题，元数据必含版本、生效日期、适用范围。适用范围丢了，答案就是错的且看不出来。
  3. 表格单独处理。拍平会丢行列关系，数字会串行。
  4. 制度更新必须重建索引，并显式下线旧版。留着旧版 = 它会用同样自信的语气引旧规则。
  5. 验收看召回命中率，不看答案正确率。答案对可能是猜的。
✎ 待补真实素材这一节的方法是通用 RAG 实践 + HR 文档特性推导，没有真实项目数据支撑。
建议补：你做员工政策问答或制度知识库时，真实的召回命中率是多少、调切片前后差了多少。一个真实的前后对比数字，比一整页方法论有说服力。

第七篇章 · 三大设计模式：循环、记忆、分身

模式三：分身，但别急着分

第三个模式是子 agent。它很好用，但也是最容易被滥用的一个——所以这一节一半在讲怎么用，一半在讲什么时候别用。

为什么需要分身

一个上下文里塞太多东西会互相干扰：你让它同时处理考勤、薪酬、组织三块，它在薪酬的口径上会不自觉沿用考勤的规则。这不是它笨，是上下文本来就是共享的。

解法是给每块活派一个独立的分身：各自有自己的任务和上下文，互不打扰，做完把结果写成文件，主 agent 再汇总。

HR 场景里真正用得上的两种
场景怎么分
多份材料并行处理三十份简历、二十份岗位说明书——每份派一个分身独立判断，避免它看完第五份之后被前面的影响（顺带解决了一个真问题：连续判断时的锚定效应）
互不相干的几块活考勤、薪酬、组织三块分别处理，各自的口径不会串
第一种对 HR 尤其有价值：人连着看三十份简历会疲劳会漂移，agent 连着看也会——因为前面的内容都在上下文里。给每份派一个干净的分身，等于每一份都是"第一份"。这是纸面流程做不到的公平性。
三条纪律
① 结果落文件，不落上下文每个分身把结果写成文件，主 agent 读文件汇总。中断了也能接着来
② 并行要可见不能"发射后不管"。主 agent 要能看到每个分身的状态和输出
③ 每个分身也要有自己的验收否则你只是把一个不可靠的判断复制了三十份
但先别急着分
这是最容易过度设计的一层并行带来速度，也带来复杂度：调试变难、出错难定位、结果不一致时更难查。
判据很简单：先把单个跑稳。如果一个 agent 处理一份简历都不够可靠，分成三十个只会让你有三十份不可靠的结果——而且你更难发现。

顺序应该是：循环（自查）→ 记忆 → 稳定之后，才考虑分身。前两个模式解决的是"对不对"，第三个解决的是"快不快"。对不对没解决之前，快是负资产。

今天就试这一节可以只读不做。如果你上一章那个 agent 还没稳定到能连续跑对三次，就先别碰分身。把这一节记在心里，等你真的遇到"活太多一个跑不完"的时候再回来。

第六篇章 · 让它认识你的活：CLAUDE.md 与项目结构

文件夹怎么摆：给它一个能干活的工位

这一节看起来最琐碎，但它决定了三个月后你的 agent 是越用越顺，还是变成一团你自己都不敢碰的浆糊。

一个够用的结构
hr-agent/ ├── CLAUDE.md ← 口径、规矩、分析模式（它每次自动读） ├── data/ ← 原始数据，只读不改 │ └── 2026-08/ ├── output/ ← 所有产出写这里 ├── scripts/ ← 固化下来的脚本 ├── specs/ ← 需求规格、分析模式规格 └── notes/ ← 它的工作笔记、历史记录
目录为什么要单独一个
data/ 只读第四篇章那条铁律的物理实现。原始数据和产出物理隔离，它就很难误伤——而且你在 CLAUDE.md 里写死"不许改 data/"之后，它每次要碰都会被自己拦下
output/产出集中，方便清理和归档。也方便你一眼看出这个月跑出了什么
scripts/固化下来的东西。这个目录的内容就是你的资产——换电脑、给同事、放作品集，拷的就是它
specs/规格文档。改需求时改这里，然后让它重新生成脚本——「修描述不修代码」的落地方式
notes/让它把工作过程记在这儿。下一章讲 harness 时你会明白这个目录有多重要
让它自己搭
帮我在当前文件夹里建好这个结构： data/（原始数据，只读）、output/（产出）、 scripts/（固化脚本）、specs/（需求与分析规格）、notes/（工作笔记） 然后在 CLAUDE.md 里加一段说明：每个目录放什么、 哪些目录不许写入。 建完把目录树打给我看一下。
一个容易忽略的收益

结构清楚之后，你可以对它下更短的指令：「把这个月的数据跑一遍」——它知道去 data/2026-08 找、按 scripts/ 里的脚本跑、结果写 output/。

这就是 agent 和聊天机器人的分界线之一：聊天机器人每次都要你把上下文说全，agent 从环境里就能知道大部分事情。而这个环境是你摆出来的。
别过度设计看到这个结构别急着建十个目录。先建 data / output / CLAUDE.md 三样就能开工，其他的等你真需要了再加。目录是长出来的，不是一开始规划出来的。
今天就试把上面那段话发给它，让它建。建完把你手上一份真实的（脱敏的）月度数据放进 data/，感受一下"它知道去哪找"是什么体验。

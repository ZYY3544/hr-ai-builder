第七篇章 · 三大设计模式：循环、记忆、分身

模式一：循环，而不是一次性回答

agent 和聊天机器人最根本的差别：聊天机器人答完就完，agent 答完会看一眼自己答得对不对。

循环长什么样
规划 → 执行 → 观察结果 → 发现问题 → 改 → 再执行 ↑ ↓ └──────────────────────────────┘

关键在「观察结果」这一步。大多数人搭出来的东西是「规划 → 执行 → 交付」，中间没有任何环节让它看到自己做的对不对。而失败信号是免费的：脚本报错、总数对不上、埋的雷没抓住——这些它都能看见，只要你让它去看。

在 HR 场景里怎么落
＃ 每次跑完数据处理，必须自己走完这个循环，不许直接交付 1. 跑完之后，先自己核对： - 结果行数 = 原表人数吗？ - 各分类加总 = 总数吗？ - specs/testcases.md 里的测试行，处理结果和预期一致吗？ 2. 有任何一条不一致：停下来，先告诉我哪里不一致， 分析可能的原因，等我确认后再改 3. 全部一致，才把结果交给我，并附上这三项的核对数字 ＃ 分析阶段同样要自查 写完分析后，逐个检查结论里的数字能不能在结果表里找到。 找不到的，删掉或标注「需要补充计算」。

注意这段话里的东西你全都学过——对总数、埋雷、数字只许引用。区别在于：以前是你手动做，现在写进 harness，它每次自动做。

这就是 harness 的本质动作：把你脑子里的检查清单，变成系统的固定环节。依赖你记得去检查，早晚有一天你会忘；写进 harness，它不会忘。
一个容易做错的地方
✕ 让它自己判断"我做得对不对"「检查一下你刚才做得对不对」——它会说「我检查了，没问题」。因为它是在用同一套理解检查同一件事，等于让人自己批自己的卷子。
✓ 给它可机械核对的标准「行数对不对」「总数对不对」「测试用例的实际结果和 specs/testcases.md 里写的预期一致吗」——这些是客观的、不依赖它的理解的。自查要有效，判据必须是它没法自圆其说的那种。
今天就试在你的 CLAUDE.md 里加一段自查循环，然后故意给它一份有问题的数据（比如少了两行），看它在交付前会不会自己发现。发现了，这一层就活了。

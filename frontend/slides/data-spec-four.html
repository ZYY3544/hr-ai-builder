第四篇章 · 需求规格：把口径写成它能执行的东西

把活写成规格：四要素

AI 写的代码出错，八成不是代码写错了，是它把你的活理解错了。而理解偏差几乎都发生在同一个地方——你没说的那部分。

先看一个会翻车的问法
✕「帮我处理下这个考勤表，算下大家的出勤率」它现在就要替你决定：分母含不含周末？含不含法定假？病假算出勤还是缺勤？月中入职的人按全月算还是按在职天数算？——每一个它都会自己拍，拍完不告诉你。

这些问题你其实都有答案，它们就是你的口径。第三篇章讲过口径是给公司建知识库的生死线，现在只是把同一个功夫用在自己的活上。

四要素
【我有什么】一份考勤表，CSV，列：工号 / 姓名 / 日期 / 打卡状态。 「打卡状态」的取值只有这几种：正常、迟到、事假、病假、年休假、缺勤。 【我要什么】每人一行的汇总表，列：工号 / 姓名 / 应出勤天数 / 实际出勤天数 / 出勤率。 期望的样子（示例行）： 1001,张伟,21,19,90.5% 【规则】 1. 应出勤天数 = 当月工作日；周末不算，法定假不算（本月假期：10-01 至 10-07） 2. 算出勤的状态：正常、迟到、年休假 3. 不算出勤的状态：事假、病假、缺勤 4. 当月入职的人，应出勤从入职日起算（入职日期见另一张表） 【注意】 - 同一人同一天有多条记录的，以「较差」的那条为准（一条正常一条缺勤 → 算缺勤） - 遇到规则 2、3 里没列出的状态值，不要自己猜，停下来告诉我 - 写代码计算，不要口算；先运行再给结果 - 结果输出成新表，不要改动原表
要素作用最容易漏的
我有什么表长什么样：列名 + 每列的取值范围取值范围。不说清「打卡状态有哪几种」，它遇到没见过的值就自己处理了
我要什么输出长什么样，直接给一行示例示例行。一行期望输出能消掉一半的理解偏差
规则你的口径，逐条编号「什么不算」。边界比中心重要——知识萃取那节讲的是同一个道理
注意脏数据怎么办 + 护栏遇到没规定的情况要停下来问。这一句把「静默自己拍」变成「举手」
两个习惯

一次一个活。「顺便再帮我算下加班时长」——别顺便。需求叠在一个对话里，它对前一个活的理解会被后一个污染。

每次新对话，四要素重新给全。它不记得你上周说过什么。好在你已经写好了——存成一个文档，下次改改就用。这个文档本身就是资产，最后一节会回来说它。

同一个活，两种问法的产出对照
✕ 一句话问法✓ 四要素
它做了什么自己定义了出勤率，直接给出一张表按你的规则算，并在开头复述了一遍它的理解
年休假算成了「假」→ 不出勤按规则算出勤
月中入职的 3 个人按全月 21 天算 → 出勤率 40% 多按在职天数算 → 90%+
重复打卡记录取了第一条取较差的那条
你会发现吗不会。表格式完好、数字正常，只是有几个人莫名其妙很低—

三处差异，没有一处会报错。而它们叠在一起，足以让你在部门会上说出一句错误的结论。

一个小动作，收益极高

四要素发过去之后，加一句：

在写代码之前，先用你自己的话复述一遍： 你打算怎么算、遇到哪几种情况会怎么处理。 我确认无误后，你再写代码。

这一步大概花你 30 秒，但它把「理解偏差」从跑完之后才发现提前到了动手之前。而且你会经常在它的复述里看到你自己都没想清楚的地方——它复述得越具体，越能照出你规格里的洞。

今天就试从你的清单里挑最烦的那个活，照四要素写一遍。写到「规则」卡住的地方——恭喜，那就是你从来没跟任何人说清楚过的口径。写下来，它比脚本值钱。
